# Security Architecture

## Authentication

Identity exposes registration and login endpoints. Passwords are hashed with
BCrypt through the `PasswordHasher` application port. Successful login returns
a JWT generated by the infrastructure `TokenGenerator` adapter.

The API is configured as an OAuth2 resource server and validates bearer JWTs on
protected requests. JWT authorities are read from the `role` claim and mapped
to Spring authorities with the `ROLE_` prefix.

## Authorization

The current HTTP policy is:

| Resource                                               | Access                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------- |
| Registration and login                                 | Public                                                        |
| `GET /api/products`, published reads, and preview URLs | Public                                                        |
| Administrator product reads and lifecycle operations   | `ADMIN` role                                                  |
| Product management writes                              | `ADMIN` role                                                  |
| Orders and customer resources                          | Authenticated user                                            |
| Stripe webhook                                         | Public HTTP route, protected by Stripe signature verification |
| OpenAPI and Swagger UI                                 | Public                                                        |
| Health and Prometheus endpoints                        | Public                                                        |
| Other routes                                           | Authenticated user                                            |

Customer-owned resources perform an additional ownership check in application
services. A valid JWT alone does not grant access to another customer's orders,
entitlements, or library assets.

## Payment Webhook Security

The Stripe webhook verifies the `Stripe-Signature` header before accepting a
payment event. Only `checkout.session.completed` events with
`payment_status = paid` can complete an application payment. The frontend
success URL is not treated as proof of payment.

## Secret Handling

Stripe keys and webhook secrets are supplied through environment variables.
MinIO credentials and endpoints are configurable through environment
variables, with development defaults in `application.yml`. Secrets must not be
committed or logged.

## Request and Error Handling

Requests receive a correlation ID through `X-Request-ID`; valid client IDs are
reused and otherwise a UUID is generated. The ID is placed in logging MDC and
removed after the request. Authorization headers, JWTs, passwords, request
bodies, payment credentials, and storage credentials are excluded from request
logging.

Unauthenticated and unauthorized requests return the same structured error
shape as application failures: `timestamp`, `status`, `code`, `error`,
`message`, `path`, and `errors`. CSRF is ignored for the stateless `/api/**`
API surface.

## Open Work

Production hardening still includes secret-manager integration, key rotation,
rate limiting, stronger operational controls around public actuator exposure,
and a formal threat model for asset delivery.

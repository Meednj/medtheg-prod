Implementation:
- Preserved the existing Payment -> Order -> OrderPaidEvent flow.
- MarkOrderAsPaidService remains transactional, validates the order and Checkout Session, verifies payment ownership, handles the completed/completed idempotent no-op, rejects partial inconsistent states, and publishes the event only after a real transition.
- Existing Order.isPaid() and Payment.isCompleted() predicates were verified and used.
- Stripe webhook signature verification and Checkout Session deserialization remain in the existing controller. checkout.session.completed is explicitly supported, payment_status must be paid, and unsupported event types are ignored with debug logging.
- Stripe PaymentGateway creation now uses the Checkout Session ID as the application provider payment ID instead of Stripe payment_intent.
- OrderPaidEvent defensively copies product IDs and rejects null event data.
- Entitlement handling uses the existing GrantEntitlementUseCase and remains outside Sales and Stripe infrastructure.

Idempotency:
Duplicate webhooks look up the application Payment by checkout_session_id. A completed Payment with a paid Order returns without saving or publishing another event. The existing Checkout Session lookup is protected by a pessimistic write lock so concurrent deliveries serialize before this check.

Stripe webhook:
The supported event is checkout.session.completed. The signed payload is verified with the existing Stripe Webhook implementation. The Checkout Session must have payment_status = paid, must contain the existing orderId metadata, and the Checkout Session ID is passed to MarkOrderAsPaidUseCase. Unsupported events are ignored and logged. Unpaid sessions do not change application state.

Payment identification:
checkout_session_id remains the application payment lookup and identity mechanism. Stripe payment_intent is not used as the application payment ID; payment creation now stores the Checkout Session ID as providerPaymentId as well.

OrderPaidEvent:
The event is published only after Payment CREATED -> COMPLETED and Order PENDING -> PAID succeed. PAID -> PAID duplicate processing publishes nothing. The immutable event payload prevents mutation after publication. Entitlement processing uses the existing customer/product idempotency behavior.

Transaction boundary:
MarkOrderAsPaidService remains @Transactional, covering the payment save, order save, and event publication registration. OrderPaidEventListener now uses @TransactionalEventListener(phase = AFTER_COMMIT), so entitlement processing observes committed payment/order state. No external message broker was introduced.

Database protection:
No new migration was added because the repository already contains the required protections:
- V7__add_checkout_session_to_payments.sql adds checkout_session_id and UNIQUE (checkout_session_id).
- V8__create_entitlements_table.sql adds UNIQUE (customer_id, product_id).
